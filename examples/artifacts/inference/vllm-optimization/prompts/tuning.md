# Propose a ranked batch of vLLM Ascend parameter candidates

Improve the current candidate on this fixed AISBench streaming workload: 160 requests, 2048 input tokens and 512 output tokens per request, concurrency 16, and request rate 0. Maximize `requestThroughput` in requests per second while working toward `ttftP90 <= 1000 ms` and `tpotP90 <= 100 ms`. Keep these workload settings and targets fixed across the baseline and every candidate. If the Recipe workload or targets are changed before an experiment, update this prompt to match them.

Selection can accept progress before both latency targets are met: no latency constraint may become more violated, and at least one violation must decrease. If every violation is unchanged, throughput must improve. A target already met must stay met. Once both targets are met, preserve both and improve throughput. A smaller violation can therefore be useful even when the candidate still misses a target; do not claim it has reached the target.

Read `candidate/tuning.json`, `context/input.json`, and `context/measurements.json`. Identify the baseline, incumbent, and measured throughput and latency. Read `target.parameterCatalog` and `maxCandidates` in `context/input.json`, and match prior `sources/` snapshots to their recorded trial results. Read the `vllm-ascend-tuning` skill before choosing candidates. Gather distinct hypotheses from the relevant specialists when their findings could change the batch. Ask `research-scout` to investigate unclear parameter behavior in the framework implementation.

Build up to `maxCandidates` independent alternatives from the same current `tuning.json`. Rank them by expected value under the benchmark constraints, highest first. Give each a coherent hypothesis and a small change that can distinguish it from other explanations. Consider a neighboring value around a winner, a supported combination, or removal of an inherited option. Compare only measured runs under the same workload. Avoid duplicates within the batch and configurations already tried. Submit fewer alternatives when evidence is limited.

Only use parameters in the supplied catalog. It permits a limited set of scheduling, cache capacity and graph execution controls supported by the installed engine. Preserve model weights, tokenizer, model and cache precision, quantization, decoding behavior, serving endpoint, NPU assignment, TP/DP/PP topology, maximum model length, benchmark workload, and software. Do not propose speculative decoding or structured `compilation_config`, `additional_config`, or other nested settings; this example does not evaluate output quality.

Return a `proposals` array in priority order. Each entry contains its own `edits` array with one `op: replace` entry for `tuning.json` containing the full new JSON as `content` and a `reason` that states the supporting evidence, expected effect, and metric most likely to regress. Include the specialist or source when it informed the candidate. Return an empty array if the available evidence supports no useful untried change. The workflow tests the alternatives serially and may stop before reaching the end of the batch. A startup or evaluation failure terminates this version of the workflow after cleanup.
