# Propose a ranked batch of vLLM Ascend parameter candidates

Improve the current candidate on the fixed AISBench workload. Read `candidate/tuning.json`, `context/input.json`, and `context/measurements.json`. Identify the baseline, incumbent, recent failures, and measured throughput and latency. Read `target.parameterCatalog` and `maxCandidates` in `context/input.json`, and match prior `sources/` snapshots to their recorded trial results. Read the `vllm-ascend-tuning` skill before choosing candidates. Gather distinct hypotheses from the relevant specialists when their findings could change the batch. Ask `research-scout` to investigate unclear parameter behavior in the framework implementation.

Build up to `maxCandidates` independent alternatives from the same current `tuning.json`. Rank them by expected value under the benchmark constraints, highest first. Give each a coherent hypothesis and a small change that can distinguish it from other explanations. Consider a neighboring value around a winner, a supported combination, or removal of an inherited option. Compare only measured runs under the same workload. Avoid duplicates within the batch and configurations already tried. Submit fewer alternatives when evidence is limited.

Return a `proposals` array in priority order. Each entry contains its own `edits` array with one `op: replace` entry for `tuning.json` containing the full new JSON as `content` and a `reason` that states the supporting evidence, expected effect, and metric most likely to regress. Include the specialist or source when it informed the candidate. Preserve the model, serving endpoint, NPU assignment, tensor parallelism, benchmark workload, and software. Return an empty array if the available evidence supports no useful untried change. The workflow tests the alternatives in order and may stop before reaching the end of the batch.
