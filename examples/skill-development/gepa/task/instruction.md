# Implement GEPA as an RSI extension

Implement the complete main algorithm of GEPA using the fixed RSI repository, its existing public interfaces and examples, and the current ember-rsi skill supplied at startup. The sole algorithm reference is the prepared GEPA v2 paper at `/opt/gepa-materials/gepa-v2.pdf`; do not consult an external implementation or an explanation derived from one. Read `/opt/gepa-materials/requirements.md` before editing.

From the paper's Section 3 and Algorithms 1–2: maintain prompt candidates, ancestry and per-instance scores; separate feedback and selection data; measure the initial candidate; sample parents by instance-leading frequency after removing dominated candidates; rotate edited modules; use sampled execution and evaluator feedback to propose a prompt; compare parent and proposal on the same minibatch; admit strict improvements, score admitted candidates on selection data, and return the best aggregate candidate within the rollout budget. Include Appendix D.1's ancestry-aware crossover, repeated-merge tracking, eligibility checks and module combination rules. Make stochastic choices reproducible. Preserve model weights and nonselected modules. A single-task integration may explicitly reuse that task across feedback and selection; document that degeneracy without changing general multi-instance behavior.

Choose the Policy/plugin decomposition yourself. Deliver `.gepa/recipe.yaml` and `.gepa/extension/index.mjs` exporting `register(registry)`, with required source and local self-tests. The Recipe must run through existing RSI startup with `--plugin-dir .gepa/extension`; its normal output must contain integer `completedRounds >= 1` after a completed proposal/evaluation round. Use the fixed Office Bundle and narrow Target in `.gepa/input/` and the fixed task `workbuddy/board-material-update-timeline-excel` for independent acceptance. No score improvement is required.

During development, run only local builds, type checks, deterministic tests and controlled simulations. The sole allowed network use is the configured model endpoint. Keep generated runtime data in `.rsi/` and one-off probes in `.scratch/`. Do not copy earlier attempts or conversations. Preserve the fixed original requirements; later acceptance issues clarify unmet requirements rather than add new ones.
