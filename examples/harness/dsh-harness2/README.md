# DSH Harness²

For each task, this example starts from a fixed baseline, executes Base once, proposes and evaluates INV and DOM improvements separately, composes a candidate from the baseline and evaluates it, then anonymously compares the final deliveries. The default selects ten distinct WorkBuddy Office tasks; configure the task list and exploration width in recipe.yaml.

At k=1, ten tasks require 40 evaluation runs. The Recipe allows 1,400 optimizer model calls and a 72-hour experiment wall budget; the evaluator retains its 4,500-second per-task timeout. The default evaluator model service has an explicit 65,536-token output limit per model turn; the configured model service must support it. This limit also applies to native judging that uses the same service. Do not also declare solver.config.maxTokens: the Evaluator SDK rejects duplicate solver and service limits.

Prepare Node 24, project dependencies, working AscendAgent-Evaluator/AgentBundle SDKs, and the Evaluator's WorkBuddy Office execution environment. Set MODEL_NAME, EVALUATOR_MODEL_NAME, MODEL_ENDPOINT, and MODEL_API_KEY in the runtime environment rather than storing their values in the Recipe. The Evaluator initializes the Agent under test; RSI does not preinstall a separate DSH instance. EVALUATOR_MODEL_NAME selects the model for evaluation execution and any native judging that selects the default service; it is required and has no fixed default. MODEL_NAME controls the optimizer Agent separately. The endpoint and credentials are inherited through the existing environment references.

Run `ember-rsi run examples/harness/dsh-harness2/recipe.yaml` from the project root. Run facts, candidates, measurements, and receipts are stored in `.rsi/`. A successful native evaluation exit does not mean the answer is correct. Inspect the Measurement's technical status, coverage, per-task results, and delivery artifacts.

This Recipe inherits the Harness² Policy's packaged Reflection configuration, but the `type: reflection` step is commented out and does not run by default. Enabling that serial step in a custom Policy permits up to 50 model calls and 600 seconds per invocation, subject to the experiment's remaining budget. Accepted guidance revisions are available to subsequent proposal calls. To replace the complete configuration, set `reflection.configFile` in the Recipe; the path is relative to the Recipe. The former `reflection: false` switch is rejected: a Policy author controls whether and where Reflection runs. Memory remains independent and can be disabled with `policy.config.memory: false`.

Proposers receive one read-only execution file per measurement with every available non-thinking event from each attempt's canonical trace, including phase/status events and complete tool calls. There is no whole-trace middle truncation. Tool-return payloads keep a prefix of 2,000 Unicode characters with explicit omission metadata (a character limit, not an exact model-token count). Read the supplied `supplementaryPath` with line ranges; the inline inventory and final-reply preview do not replace the event sequence. Unavailable source evidence remains explicitly unknown.

Component bindings, Prompts, and the editing Skill use the Harness² Policy's default assembly. The Recipe configures the application, Policy parameters, evaluator benchmark/model services and budget. Benchmark-specific evaluator settings belong to the Recipe rather than Policy defaults. agent explicitly binds agent.pi and reads MODEL_NAME, MODEL_ENDPOINT, and MODEL_API_KEY by default. Override the relevant component configuration in the Recipe's bindings when customization is needed.

For proposal audits, each optimizer `agent` call retains `diagnostics.jsonl` under the experiment call directory: completed assistant messages, tool starts/results, validation failures/recovery and terminal errors. Its persisted call receipt contains the actual prompt, structured input, authorized virtual files and validated final response. Link these child calls to the INV/DOM, Composer and Memory parent calls to distinguish generated edits, committed candidate changes and valid no-change results. Benchmark Agent execution traces are retained separately through each Measurement's authorized evidence index.
